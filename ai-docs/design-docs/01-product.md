# 01 · 产品定义与范围

## 背景

前端/全栈项目在开发或验收阶段经常需要「把本机服务临时给别人看一眼」：设计师看样式、后端联调回调、客户在手机上看效果、CI 里跑一次真机冒烟。现实中通常有三条路：

1. 用 `cloudflared tunnel --url`、`ngrok`、`localtunnel` 之类的临时隧道。命令要自己拼，域名是随机的 `*.trycloudflare.com` / `*.ngrok-free.app`，无法用自己的域名，也没人负责清理。
2. 在 Cloudflare 控制台手工建 Named Tunnel、配 ingress、加 CNAME，再把 token 填给 `cloudflared`。步骤多、易残留，用完常常忘记删 DNS 和隧道。
3. 部署到测试环境。链路长，不适合「改一行看一眼」。

`flash-tunnel` 把第 1 条的「一条命令」和第 2 条的「自己的域名」合起来，并补上缺失的一环：**退出即清理**。

## 目标用户与场景

| 场景 | 描述 | 关键诉求 |
| --- | --- | --- |
| 本地预览分享 | 前端同学把 `pnpm dev` 的页面发给设计/产品 | 一条命令、链接短、可复制、退出即失效 |
| 后端联调回调 | 需要公网 HTTPS 回调地址（OAuth、支付、Webhook） | 固定域名可预期、HTTPS、可重复运行 |
| 移动端真机验收 | 手机扫码打开本地页面 | 终端可出二维码（后续）、局域网无关 |
| CI/自动化预览 | PR 构建产物临时预览，任务结束即销毁 | 非交互、可拿到 URL、退出码可靠、无残留 |
| 多项目并行 | 同时开多个仓库，各自一个临时域名 | 子域名不冲突、互不误删 |

## 产品目标

### 必须（MVP）

1. `npx flash-tunnel` 在无配置文件时也能跑通：自动识别项目、启动本地服务、建立 Cloudflare Named Tunnel、创建自有域名 CNAME、输出 HTTPS 地址。
2. 退出（正常结束、`Ctrl+C`、`SIGTERM`、未捕获异常）后，本次创建的 DNS 记录与 Tunnel 必须被删除；删除失败要有明确报错与再次清理入口。
3. 进程被强杀（`kill -9` / 断电）后，下次运行能识别并清理该项目的遗留资源，或至少在 `flash-tunnel clean` 中可清理。
4. 支持可选的 `flash-tunnel.ts` 配置（只用 `.ts`），可覆盖：启动命令、端口/地址/静态目录、域名、隧道名、供应商、自动停止时长；所有配置项都有可推导的默认值。
5. 域名与隧道通过适配器实现，当前只实现 Cloudflare；新增供应商不需要改核心流程。
6. 失败可回滚：任何一步失败都不会留下「半套」资源（隧道建了但 DNS 没建、DNS 建了但 cloudflared 没起来）。

### 应当（GA 前）

- `flash-tunnel doctor`：检查 cloudflared、Token 权限、Zone、端口占用、域名冲突、Vite `allowedHosts` 等常见坑。
- `flash-tunnel clean`：按会话、项目或全量清理遗留资源，支持 `--dry-run`。
- `--json` / `--ready-file`：给 CI 与其它脚本消费。
- 断线自动重连提示、隧道健康检查、启动耗时诊断。
- 终端步骤行（颜色 + spinner + 交互选择）；二维码、剪贴板复制、浏览器自动打开（TTY 默认开启，`--no-open` 关闭）。
- 可选 `autoStopAfter`：到期自动停止并清理，缩短临时链接的暴露窗口。

### 可以（后续）

- 更多供应商：frp（自建服务端）、ngrok、其他 DNS（DNSPod、阿里云、Route53）。
- 固定子域名与域名池（写死模板、复用记录）。
- Cloudflare Access 一键加保护（邮箱/OTP）。
- 监听构建产物变化自动重载页面（与 dev server 的 HMR 互补）。
- 团队共享：把临时域名登记到内部面板，到期自动回收。

## 非目标

- **不做通用反向代理/网关**：不承担生产流量、不做负载均衡、不做鉴权网关（Access 仅作为可选项）。
- **不做内网穿透服务端**：不自建中继；连接能力全部来自供应商适配器。
- **不管理生产 DNS**：只增删带本工具标记的记录，绝不修改既有记录或按通配符批量删除。
- **不做多用户/多租户平台**：CLI 单机使用，凭据来自本机环境变量。
- **不替代部署**：临时链接不是发布环境，不保证可用性与持久化。

## 与现有工具的差异

| 能力 | `cloudflared tunnel --url` | ngrok | localtunnel | flash-tunnel |
| --- | --- | --- | --- | --- |
| 自有域名 | 否（`trycloudflare.com` 随机） | 付费计划 | 否 | 是（Cloudflare 托管的 Zone） |
| 自动识别并启动项目 | 否 | 否 | 否 | 是（含 monorepo 探测） |
| 退出自动删除 DNS/Tunnel | 否 | 否 | 否 | 是（含崩溃兜底） |
| 供应商可替换 | 否 | 否 | 否 | 是（DNS/隧道双契约） |
| 配置文件 | 无 | yml | 无 | `flash-tunnel.ts`（可选） |
| CI 友好 | 一般 | 一般 | 一般 | `--json` / `--ready-file` / 可靠退出码 |

## 验收标准

以「一个从未配置过 Cloudflare 的开发者」为基准，按以下步骤验收：

1. 设置 `CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`（或仅 Token），在任意含 `dev`/`preview` 脚本的仓库执行 `npx flash-tunnel`。
2. 60 秒内终端输出可访问的 `https://<子域>.<zone>`，浏览器打开返回本地页面。
3. 按 `Ctrl+C`，30 秒内退出；Cloudflare 控制台该 DNS 记录消失、Tunnel 列表无该隧道；再次访问域名返回 DNS 解析失败或 530。
4. 重复执行 3 次，不产生任何遗留 Tunnel / DNS 记录。
5. 强杀进程后再执行一次，日志提示「发现并清理遗留资源」，随后正常建立新会话。
6. 把 Token 改成只有 DNS 权限，运行应给出可读错误（缺少 Cloudflare Tunnel Edit），且不创建任何资源。
7. 在 `pnpm-workspace` 仓库根目录执行，能定位到含 `dev`/`preview` 的子包，或在交互模式下列出候选包。

## 成功指标（内部）

- 冷启动到输出链接：P50 < 15s（不含首次 cloudflared 下载）。
- 清理成功率：正常退出 100%，异常/崩溃场景下次运行可回收 ≥ 99%。
- 误删生产记录：0（以「只按记录的 id + comment 校验」为保证）。
- CLI 首次使用者成功率：≥ 80%（doctor 能解释失败原因）。

## 关键假设与风险

| 假设 | 风险 | 验证方式 |
| --- | --- | --- |
| 通过 REST API 创建 `config_src=cloudflare` 的隧道会直接返回 token | 若某类账号不返回 token，则需再调 `/token` 接口或改用本地 cert 模式 | M0 期间用真实账号打通（见 12 文档 S1） |
| 停止 cloudflared 后连接会在数秒内断开，随后可删除隧道 | 连接残留时删除会失败，需要 `/connections` 清理接口兜底 | 同上 |
| 用户愿意提供 Account 级 Token | 安全敏感用户可能拒绝；需文档说明最小权限与临时 Token | 09 文档 + doctor 引导 |
| 随机子域名不会撞车 | 同一 Zone 高频运行可能冲突；需要重试与冲突检测 | 04 文档的命名与冲突策略 |
